# Дотримання принципів програмування в коді

`Money.cs`

1. **DRY (Don't Repeat Yourself)**:
   Код не повторюється. Ми використовуємо метод `isCorrectMoney` для перевірки коректності грошових одиниць у декількох місцях.

2. **SOLID (5 окремих принципів)**:
   - **Single Responsibility Principle (Принцип єдиного обов'язку)**:
     Клас `Money` відповідає лише за представлення грошей та проведення операцій над ними.
   - **Open/Closed Principle (Принцип відкритості/закритості)**:
     Клас `Money` може бути розширений для додавання нових операцій через створення нових методів.

3. **KISS (Keep It Simple, Stupid)**:
   Код класу `Money` має просту структуру та чіткі методи, які реалізують базові операції з грошима.

4. **YAGNI (You Aren't Gonna Need It)**:
   Ми реалізуємо лише те, що потрібно наразі для представлення та операцій з грошима.

5. **Composition Over Inheritance (Композиція над успадкуванням)**:
   У цьому коді ми використовуємо композицію, а не успадкування. Клас `Money` не успадковує жодного іншого класу.

6. **Program to Interfaces not Implementations (Програма до інтерфейсів, а не реалізацій)**:
   Хоча у цьому конкретному коді немає використання інтерфейсів, але цей принцип може бути дотриманий шляхом використання інтерфейсів для різних операцій з грошима.

7. **Fail Fast (Швидка реакція на помилки)**:
   Методи класу `Money` перевіряють коректність даних та генерують виключення в разі некоректних вхідних даних або операцій.

`Reporting.cs`
1. **Single Responsibility Principle (Принцип єдиного обов'язку):**
   Клас `Reporting` відповідає лише за збір та надсилання повідомлень про події в системі, такі як додавання товару, його видалення або наявність товарів на складі.

2. **Open/Closed Principle (Принцип відкритості/закритості):**
   Клас `Reporting` може бути розширений для додавання нових типів повідомлень без модифікації власного коду. Він отримує залежність через конструктор, що робить його гнучким для використання з будь-якими функціями обробки повідомлень.

3. **Liskov Substitution Principle (Принцип підстановки Лісков):**
   Клас `Reporting` може бути використаний в будь-якому місці, де потрібен об'єкт, що реалізує інтерфейс `IReporting`, без змін у способі використання.

4. **Interface Segregation Principle (Принцип розділення інтерфейсу):**
   Інтерфейс `IReporting` містить лише методи, що пов'язані з функціональністю звітності, що дозволяє класам реалізувати цей інтерфейс без перенесення зайвого функціоналу.

5. **Dependency Inversion Principle (Принцип інверсії залежностей):**
   Клас `Reporting` отримує свою залежність (у вигляді делегата `Action<string>`) через конструктор, що дозволяє використовувати його з будь-якими функціями обробки повідомлень без прив'язки до конкретних реалізацій.

`Warehouse.cs`

1. **Single Responsibility Principle (Принцип єдиного обов'язку):**
   Клас `Warehouse` відповідає за збереження та управління товарами на складі. Він несе відповідальність лише за виконання операцій з товарами, а робота з репозиторієм делегована іншому класу.

2. **Open/Closed Principle (Принцип відкритості/закритості):**
   Клас `Warehouse` може бути розширений для додавання нових функціональностей через використання репозиторію як абстракції. Зміни у репозиторії не потребують змін у коді складу.

3. **Dependency Inversion Principle (Принцип інверсії залежностей):**
   Клас `Warehouse` отримує залежність від репозиторію через його інтерфейс `IWarehouseRepository`. Це дозволяє легко замінювати конкретну реалізацію репозиторію без змін у коді складу.
   
 `WarehouseRepository`  
1. **Single Responsibility Principle (Принцип єдиного обов'язку):**
   Клас `WarehouseRepository` відповідає за збереження та управління товарами на складі через взаємодію з базою даних. Він також відповідає за відправлення повідомлень про події в системі, такі як додавання або видалення товару, використовуючи інтерфейс `IReporting`.

2. **Open/Closed Principle (Принцип відкритості/закритості):**
   Клас `WarehouseRepository` може бути розширений для взаємодії з різними джерелами даних (наприклад, базами даних різних типів) шляхом реалізації іншого інтерфейсу, який спадає від `IWarehouseRepository`.

3. **Dependency Inversion Principle (Принцип інверсії залежностей):**
   Клас `WarehouseRepository` отримує залежність від контексту бази даних та об'єкта, який відповідає за повідомлення про події, через конструктор. Це дозволяє легко замінювати реалізацію бази даних та об'єкта звітності без змін у коді класу `WarehouseRepository`.
